# Task 拆分

只有在 Spec 与变更预算自洽后，才创建 DAG。

## Task 质量

每个 Task 只承担一个行为或工程职责，并包含：稳定 ID/标题、当前 Spec 版本、AC ID、依赖、`latest_verified_integration_sha` 基线策略、允许/受保护路径、相近参考实现、预期交付物、验证预期、风险，以及适用时的明确非范围。Task 必须可以独立实现、审核和测试，不能暗中完成第二个 Task。

按稳定所有权或依赖边界拆分，不能机械按文件或技术层拆分。如果把 Controller/Service/Data 拆开会导致任何部分都无法独立产生意义，则保持纵向切片完整。只有上线或兼容性要求顺序时，才优先拆出迁移/契约 Task。

## Root Issue、阶段与环境边界

Task 只拆一个已批准交付阶段内的工作。若一组行为能独立产生用户价值并拥有独立发布、权限、环境或验收边界，应先由规划者拆为另一个 Root Issue 或阶段，而不是把一个 Program/Epic 塞入巨大 DAG。跨阶段关系通过现有 Root Issue/Decision 文本引用，不改变 Task Schema；完整能力清单必须保留。

区分合成/Mock、本地真实边界、集成环境、live 服务和生产授权验证。能够独立验收时，将不可用环境对应的验证切片与本地实现分开，只阻塞受影响部分；若一个 Task 的必需 AC 只能依赖当前不可获得的权限或环境且不能拆分，该 Task 必须保持 `BLOCKED`，不得以较低权威结果替代。

## DAG 检查

- Spec 中每个验收标准都映射到一个或多个 Task，随后还要映射到测试用例。
- 每个 Task 都必须贡献于某个 AC、必需风险控制、迁移、文档或验证结果。
- 依赖必须必要且无环；通过拓扑排序确认。
- Task 不能依赖会移动的分支。只有进入 `READY` 时才设置具体 `base_ref`/`base_sha`。
- 修改共享公开契约、数据库对象、构建文件、共享配置或同一 UI/模块区域的 Task 应串行执行，除非能证明所有权互不重叠。
- 生成产物必须注明生成器源和命令。
- Brownfield Task 必须留在已批准变更预算内。潜在清理应另建后续工作，不能作为隐藏依赖。
- Task 的验证预期必须注明实际环境层级、所需授权、可用性证据和更低层结果不能证明的事项。

## 就绪条件

只有满足以下全部条件时才标记 `READY`：所有依赖均为 `VERIFIED`；Spec/测试批准仍为当前有效；最新集成 SHA 已知且干净；worktree 隔离安全；允许/受保护路径精确；本 Task 必需的环境和权限已具备；写入区域只由一个实现者负责。否则保持 `PLANNED`，或带原因标记为 `BLOCKED`。

## 独立修订与完整交付预算

v2 每个 Task 在 current 中使用稳定 ID 和独立 revision，仅受影响对象更新；当前状态由 state 索引，不能复制 Task 全文进去。Task 的 spec_version 表示实际批准的行为基线，父文档其他章节变更不要求机械换号，沿用按变更控制提供适用性依据。

预算包含测试、生成物、必要文档和余量；宿主定义了行数/字节硬限制时沿用其计数口径。未定义时不另造全局硬阈值。仅预算/依赖调整作局部技术复审，不把所有 Task 复制到 tasks-v*，不重建无关计划。
