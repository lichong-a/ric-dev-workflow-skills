# 产物生命周期

DevFlow 产物是持久的交接证据。对话历史不是事实来源。

## 位置与身份

产物存放在 `.devflow/changes/<REQ-ID>/` 下，并使用稳定标识符：

- Root Issue：`REQ-YYYYMMDD-NNN`
- Task：`TASK-NNN`
- Review：`REVIEW-NNN`
- Test 或 Report：`TEST-NNN`
- Implementation：`IMPL-NNN`
- Defect：`DEFECT-NNN`
- Decision：`DECISION-NNN`

若仓库已有不会冲突的 ID 约定，可以沿用，但所有引用必须明确。

## 草稿、发布与取代

- 规划者拥有的规划类产物，在明确标记为草稿、尚未送交独立 Reviewer 且未被 `state.yaml` 引用时，可以原地完善；内部预检和自审不需要制造新的正式版本。
- 某个产物一旦被送交独立 Reviewer、产生独立审核结论或被 `state.yaml` 引用，即视为已发布。无论结论是批准、请求修改还是阻塞，被审核版本都必须冻结。
- 已发布的审核、测试报告或实现报告绝不能覆盖修改。
- 修正必须使用新的 ID/版本发布，并把 `supersedes` 指向旧产物；随后由规划者将状态指向最新有效产物。
- 保留旧证据，使读者能够还原门禁结论变化的原因。
- 局部修订只发布实际变化的产物；未变化的 Root Issue、仓库画像、测试证据或 Decision 使用原路径、版本和身份引用，不得复制整套材料。

审核者按要求在只读 Custom Agent 中运行时，通过向规划者返回完整结构化审核来完成发布。规划者可以把该载荷原样写入声明的新产物路径；这只是传输，不代表规划者拥有作者身份或批准权。若持久化必须改动载荷，则审核者必须另行发布新产物。

## 证据绑定与失效

| 产物 | 必须绑定到 | 何时失效 |
|---|---|---|
| Spec 审核 | 精确 Spec 版本 | 被审核 Spec 的含义变化 |
| 用户批准 | 精确 Spec 版本 | Spec 发生行为变更 |
| 测试审核 | Spec 与测试计划版本 | 任一相关版本变化 |
| 代码审核 | `base_sha..head_sha`、Task、Spec 版本 | head 或相关 Spec 变化 |
| 测试报告 | `tested_sha`、Spec、测试计划版本 | 代码或相关计划变化 |
| 发布审核 | 精确集成 SHA 与当前证据集 | 集成 SHA 或证据发生变化 |

已发布产物即使只是编辑性修改，也必须递增版本。含义未变时，审核者可以记录快速确认；技术性变更必须重新审核；行为变更则按 `change-control.md` 使下游批准失效。尚未发布的草稿可以在同一草稿版本内完成编辑和预检。

## 状态引用

只有规划者可以更新 `state.yaml`。状态只能引用确实存在、匹配当前有效版本和 SHA，且未被取代或判定失效的产物。若证据无法协调一致，应转入 `BLOCKED`，不得伪造连续性。
