# Brownfield 与续作策略

只要范围内存在业务代码、历史、测试、契约、用户、部分实现、迁移或未提交改动，就按 `BROWNFIELD` 处理。若请求路径已被部分实现、仅有桩或 mock、曾被放弃，或要从某个功能分支继续，则使用 `BROWNFIELD_CONTINUATION`。

## 设计或修改生产代码前的必需侦察

1. 记录 Git 根目录、分支、HEAD、upstream、目标分支证据和 worktree 状态。
2. 阅读所有适用的 `AGENTS.md`/override，以及与任务相关的项目、架构、贡献、构建和 CI 指南。
3. 从清单、锁文件、配置、生成类型和 CI 推导语言、运行时、依赖、构建、测试及格式规则。
4. 追踪请求行为的真实入口、调用链、数据/公开/权限边界和部署路径。
5. 选择两到三个近期、稳定且邻近的参考实现及其测试，并记录路径、符号和相关性。
6. 盘点已完成、部分完成、桩、冲突、已放弃、未知和未开始的工作。
7. 在记录的 SHA 上运行可行的基线检查，并对失败分类。
8. 识别生成代码、vendor、锁定文件、迁移和受保护区域。

## 仓库事实优先级

优先级从高到低为：当前用户请求和已批准 Spec；最近作用域的指令；强制执行的格式化器、Lint、编译器、类型检查、测试与 CI；公开契约和实际运行时；邻近稳定实现；仓库多数实践；文档；通用实践。若本地模式存在安全或正确性问题，应以最小且有记录的差异优先保证安全和正确。

## 续作清单

将每个相关单元分类为 `ACCEPTED_COMPLETE`、`COMPLETE_UNVERIFIED`、`PARTIAL`、`STUB`、`CONFLICTING`、`ABANDONED`、`UNKNOWN` 或 `NOT_STARTED`。优先保留并补全已有纵向路径；若确实必须重写，应说明理由。

## 强制变更预算

每个 Brownfield Root Issue 都必须记录：变更半径、允许/受保护路径、公开契约与数据库策略、依赖/框架/构建限制、格式化范围、生成文件策略、重构策略和写入者限制。默认禁止新增依赖、迁移框架或构建系统、大范围重命名/移动、全仓格式化、清理无关技术债，以及未经批准的契约变更。

提议的重构必须分类为 `REQUIRED`、`INCIDENTAL` 或 `OPPORTUNISTIC`。默认只有必要重构属于当前范围；审核者可以允许极小的伴随改动。机会型想法应另行记录。

## 基线失败与特征测试

对每条命令记录 SHA、结果、分类（`clean`、`pre_existing`、`environment` 或 `unknown`）及证据。不得把已证明无关的既有失败归咎于当前工作，也不得把新增失败冒充成历史问题。本次变更不能扩大失败集合。当受影响行为必须保持但缺少可信覆盖时，添加窄范围特征测试；不要固化明显缺陷，也不要生成脆弱的大型快照。
