# 变更控制

## Spec 变更

每次修改已发布 Spec 时都必须分类：

- `EDITORIAL`：拼写、格式或措辞变化，但含义完全一致。递增版本并取得审核者的快速确认；可以不要求用户重新批准。
- `TECHNICAL`：内部拆分、已批准的实现约束或变更预算调整，不改变外部行为。递增版本，重新执行 Spec 审核，并重新计算受影响 Task。
- `BEHAVIORAL`：验收标准、API、数据、UI 行为、权限、错误、兼容性或安全边界发生变化。递增版本；使此前的 Spec 审核、用户批准、测试计划审核及受影响代码/测试证据失效；返回 G2/G3/G4。

记录分类、原因、变更章节、受影响的 Task/证据和决策。

尚未送审、未产生独立结论且未被状态引用的草稿可以原地完善，不属于已发布 Spec 变更。不得为内部预检或措辞迭代连续发布版本；一经送审，即使审核未通过也必须按上述规则发布后续版本。

## Commit 与证据变化

- 代码审核只证明一个 `base_sha..head_sha`；head 变化后该审核失效。
- 范围狭窄的修正可以接受有记录的增量复审；默认由仍保持独立且可用的原 Reviewer 检查待关闭 Finding、精确 Delta 和受影响邻域。架构性、行为性、广泛变更或显著风险扩张必须完整复审。
- 测试报告只证明一个 `tested_sha`；后续代码变化必须重新生成运行证据。
- 发布审核只证明一个集成 SHA 及其引用的证据集。
- 会移动的分支名绝不能替代不可变 SHA 身份。

## 范围增长

不得把新需求伪装成 Defect。规划者应依据行为边界、依赖和发布风险，选择发布新 Spec 版本、创建新 Task 或拆分为独立 Root Issue。若范围增长改变产品行为或重要取舍，必须取得用户批准。

## 审核修正与收敛

Reviewer 必须在一次可完成的正式审核中返回当时可识别的全部 P0/P1/P2 Finding。每个 Finding 使用稳定 ID；后续版本逐项记录 `resolved`、`unresolved`、`accepted` 或 `not_applicable` 及其证据，未解决项沿用原 ID，新问题使用新 ID。`accepted` 只允许用于具有当前有效风险接受的 P2；P0/P1 不得通过风险接受放行。

同一产物和审核模式连续两次 `REQUEST_CHANGES` 仍未收敛时，规划者必须暂停继续送审，汇总重复和新增 Finding，并把根因归为事实预检、Spec 结构、测试模型、架构约束或范围失控。完成针对性修正或重新规划后才能开始下一轮正式审核。该审核收敛计数不替代下面的 Defect 三轮规则。

同一 Defect 连续三轮处理后仍然存在时，应停止补丁式修复。规划者发起根因分析，审核者重新评估 Spec、架构和测试模型，并在下一次实现尝试前重新规划。
