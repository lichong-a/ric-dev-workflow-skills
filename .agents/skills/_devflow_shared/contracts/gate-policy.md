# 门禁策略

门禁用于防止某个角色把自己的断言直接变成交付事实。

| 门禁 | 必需输入 | 通过证据 | 决策所有者 |
|---|---|---|---|
| G0 需求接收 | 开发请求 | Intake（v2 为 current 中的对应章节；v1 为 intake.md） | 规划者 |
| G1 仓库基线 | Brownfield 范围 | 仓库画像、接管评估、基线；风险要求时还需审核 | 审核者 |
| G2 Spec | Root Issue、Spec、UI/技术决策、DAG | 对应版本的 `SPEC_REVIEW: APPROVE` | 审核者 |
| G3 用户批准 | 已审核的产品行为与重要取舍 | 绑定 Spec 版本的用户批准 | 用户 |
| G4 测试计划 | 已批准 Spec | 对应计划版本的 `TEST_REVIEW: APPROVE` | 审核者 |
| G5 Task 代码 | 已批准 Task 的完整候选及各代码作者报告，含必要测试 | 对应 SHA 范围的 `CODE_REVIEW: APPROVE` | 审核者 |
| G6 Task 集成 | Task 已合并至集成分支 | 对应 SHA 的增量测试 `PASS` | 测试者 |
| G7 完整验证 | 所有 Task 均已验证 | 对应集成 SHA 的完整测试报告 `PASS` | 测试者 |
| G8 发布 | 当前验证证据及迁移/配置/回滚文档 | 对应 SHA 的 `RELEASE_REVIEW: APPROVE` | 审核者 |
| G9 合并后验证 | 已合并至实际目标分支 | 对应目标 SHA 的冒烟测试 `PASS` | 测试者 |
| G10 完成 | 所有证据均为当前有效 | 关闭记录及 `DONE` 状态 | 规划者 |

事实预检、交付规模判断和目标仓库协议映射是进入首次 G2 前的准备工作，不新增 Gate 或状态。目标仓库已有证据只有在语义范围、独立决策所有者、版本/SHA 绑定和时效性均等价时，才能直接满足对应 Gate；`state.yaml` 引用其原始身份，不复制内容。规则冲突时执行更严格的一项。

环境或授权缺失应尽量限定到可独立验证的 Task/切片。低权威的合成、本地或 Mock 结果不能替代 G6–G9 要求的集成、live 或目标分支证据；不可拆分的必需证据缺失时，对应 Gate 必须保持未通过。

## 审核适用范围与直接省略

G0–G4 是当前 Root/阶段的共享准备，不为每个 Task 或实现步骤重跑；G5/G6 面向完整 Task 候选及其集成 SHA；G7–G10 面向当前交付的最终验收。角色动作不是 DAG 节点，门禁也不递归套在门禁动作上。

Tester 编写的测试属于原 Task 候选，不单独建立测试 Task。G5 后新增/修正测试代码仍使相关候选证据需要重新绑定，按[测试代码交付](../../devflow-tester/references/test-code-delivery.md)完成代码复审与 G6；测试计划审核不能替代测试代码审核。G6 后 Task 保持 `VERIFIED`，G9 通过及关闭条件齐备后才进入 `DONE`。

Planner 在初始规划的现有 Decision/Task notes 中简记适用门禁和已有证据；不创建逐步骤审核矩阵或新 Schema。以下情况可直接不发起额外 Reviewer 调用，不必先找 Reviewer 批准“无需审核”：

- Task 内部实现顺序、检查点、自测、生成物和必要文档步骤：并入完整候选 G5，不逐项送审。
- 无相关 UI/数据/权限等边界的专项维度，以及不满足 Brownfield/Continuation 风险触发条件的额外 BASELINE_REVIEW：注明不适用依据；必须的仓库画像/基线事实仍保留。
- 对象及必要输入均未变、原绑定仍有效，或宿主已有等价独立证据：引用原身份与覆盖范围，不重复发起同模式审核。
- 仅过程清单/进度变化，或明确无语义影响的 EDITORIAL：按变更控制记录，不单独开审。

“省略额外调用/不适用”不是新的 Verdict、状态或 APPROVE。仍适用的 G2/G3/G4/G5/G8 不能因“小任务、赶时间、DAG 已冻结”跳过；代码 SHA 改变、真实阻断 Finding、权限/行为/测试预期变化也不能借此沿用失效证据。Reviewer 只检查委派对象的适用维度，不要求每个步骤成为独立审核节点。宿主明确强制的审核仍执行。

## 交付深度

- `FAST`：允许紧凑的 Mini Spec 和测试计划；但仍须保留角色分离、精确证据、对行为变化的用户批准，以及所有适用门禁。
- `STANDARD`：使用完整产物和常规审核/测试深度。
- `HIGH_RISK`：增加威胁、权限、迁移、回滚、失败恢复、审计及有依据的性能覆盖。明确的风险接受只能处理 P2；P0/P1 始终阻塞。

任何角色都不能因“没有反馈”而推定通过。身份/授权/关键证据缺失导致无法审核时为 `BLOCKED`；对象可审核但有阻断 Finding 时为 `REQUEST_CHANGES`。局部修订按变更控制复核实际影响，未变对象不因父文件修订而重开门禁。
