# 角色边界

本契约是单个 DevFlow Root Issue 内所有权和职责分离的权威规则。

## 所有权矩阵

| 活动或产物 | 规划者 | 审核者 | 测试者 | 实现者 |
|---|---|---|---|---|
| 需求接收、Root Issue、Spec、UI Spec、DAG、变更预算 | 负责 | 审核 | 读取 | 读取 |
| 仓库画像与接管评估 | 负责 | 必要时审核 | 贡献测试基线 | 读取 |
| `state.yaml` 与 Defect 归因 | 唯一写入者 | 读取 | 读取 | 读取 |
| 审核产物 | 读取并引用 | 唯一作者 | 读取 | 读取 |
| 测试计划、测试自动化、报告、Defect 证据 | 协调 | 审核计划/证据 | 负责 | 仅负责单元/组件测试 |
| 生产实现与实现报告 | 协调 | 审核 | 验证 | 每次负责一个 Task 或 Defect |
| 集成与目标分支合并 | 负责 | 发布门禁 | 验证合并后 SHA | 绝不合并 |

只读审核者始终是审核内容的唯一决策作者。它向规划者输出完整 YAML 载荷；规划者可以将载荷原样持久化，然后更新状态。规划者不得修改结论或发现。任何内容修改都必须由审核者发布新的审核产物。

## 职责分离规则

1. 任何角色不得批准自己创建或修改的产物。
2. 规划者不得编写生产代码，也不得修复合并冲突中的代码。
3. 审核者不得修改被审核对象，只能发布新的审核产物。
4. 测试者可以修改测试代码和测试产物，但不得修改生产代码、已批准行为，也不得仅为通过而修改断言。
5. 实现者每次只能处理一个已批准 Task，或一个归因于 `IMPLEMENTATION` 的 Defect；不得修改已批准 Spec、自审批准、合并或关闭 Root Issue。
6. 同一 Root Issue 在任一时刻只能由一个规划者负责全局状态。
7. 请求动作跨越角色边界时，应返回 `BLOCKED` 并说明缺失的交接，或把工作交给拥有该职责的角色。不得悄悄兼任两个角色。

## 必需交接身份

每次交接必须注明 Root Issue、单一角色操作、产物路径、相关版本、精确源/base/tested Commit SHA、适用的 Finding/Defect、允许/受保护路径、预期输出和停止条件。完整材料通过持久路径和不可变身份引用，不重复粘贴，也不依赖完整对话历史。无法从有效状态推导的身份、权限或版本不得由接收角色猜测；“审核一下”或“完成它”之类的请求并不充分。
