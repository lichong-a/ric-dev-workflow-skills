# 角色边界

本契约是单个 DevFlow Root Issue 内所有权和职责分离的权威规则。

## 所有权矩阵

| 活动或产物 | 规划者 | 审核者 | 测试者 | 实现者 |
|---|---|---|---|---|
| 需求接收、Root Issue、Spec、UI Spec、DAG、变更预算 | 负责 | 审核 | 读取 | 读取 |
| 仓库画像与接管评估 | 负责 | 必要时审核 | 贡献测试基线 | 读取 |
| `state.yaml` 与 Defect 归因 | 唯一写入者 | 读取 | 读取 | 读取 |
| 审核产物 | 读取并引用 | 唯一作者 | 读取 | 读取 |
| 测试计划、测试自动化、报告、Defect 证据 | 协调 | 审核计划/证据 | 负责 | 仅负责单元/组件测试 |
| 生产实现与实现报告 | 协调 | 审核 | 验证 | 每次负责一个 Task 或 Defect |
| 集成与目标分支合并 | 负责 | 发布门禁 | 验证合并后 SHA | 绝不合并 |

只读审核者始终是审核内容的唯一决策作者。它向规划者输出完整 YAML 载荷；规划者可以将载荷原样持久化，然后更新状态。规划者不得修改结论或发现。任何内容修改都必须由审核者发布新的审核产物。v2 对所有角色采用同样的原样转录规则：Tester 拥有 test-plan，Planner 拥有 current/state 和账本串行追加权，Reviewer 保持只读。账本汇聚存储不改变原始作者、批准权或生产代码边界。

## 职责分离规则

1. 任何角色不得批准自己创建或修改的产物。
2. 规划者不得编写生产代码，也不得修复合并冲突中的代码。
3. 审核者不得修改被审核对象，只能发布新的审核产物。
4. 测试者可以修改测试代码和测试产物，但不得修改生产代码、已批准行为，也不得仅为通过而修改断言。
5. 实现者每次只能处理一个已批准 Task，或一个归因于 `IMPLEMENTATION` 的 Defect；不得修改已批准 Spec、自审批准、合并或关闭 Root Issue。
6. 同一 Root Issue 在任一时刻只能由一个规划者负责全局状态。
7. 请求动作跨越角色边界时，向负责的 Planner（独立调用时向调用者）返回精确缺口；需要时为 `BLOCKED`。不得悄悄兼任角色或自行委派另一个角色。

## 单层调度，不递归研发

只有当前 Root 的 Planner 可以创建正式 Task 和直接调度角色；不得为每个 Task 再启动 Planner。Reviewer、Tester、Implementer 仅完成交接动作，不创建子 Root/Task、不重规划 DAG、不再派生 DevFlow 角色。独立只读侦察确有必要时由 Planner 直接调度，不能派生规划—实现—测试—审核链。

“调度”指决策所有权。Codex 保持原调用方式；Claude Code / ZCode 按[原生平级调用](../../devflow-planner/references/orchestration.md#原生平级调用)由唯一 Planner 子代理决定动作，主会话仅代为发起同级调用和原样回传，不是第二个 Planner 或第五个角色，也没有规划、状态或证据写入权。四个子代理都不再派生代理，包括通过命令行绕行。宿主转发不改变上面的所有权矩阵。

实现者可以在一个 Task 内维护步骤和检查点、分步实现与自测；这些不是新的审批对象。测试者把用例分组，审核者按维度检查，也不能把这些内部步骤升级成子任务。角色完成或遇到职责外问题后交回同一 Planner；会话恢复不创建新的任务层级。粒度和改图例外见[Task 与冻结 DAG](../../devflow-planner/references/task-decomposition.md)。

## 必需交接身份

每次交接必须注明 Root Issue、单一角色操作、产物路径、相关版本、精确源/base/tested Commit SHA、适用的 Finding/Defect、允许/受保护路径、预期输出和停止条件。完整材料通过持久路径和不可变身份引用，不重复粘贴，也不依赖完整对话历史。无法从有效状态推导的身份、权限或版本不得由接收角色猜测；“审核一下”或“完成它”之类的请求并不充分。
