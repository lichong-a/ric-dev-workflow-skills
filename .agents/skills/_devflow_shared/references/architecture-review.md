# 架构审核

仅当 Spec、代码或发布范围改变模块边界、依赖、执行拓扑或重要横切逻辑时，加载本参考。

## 以证据驱动审核

- 绘制本次变更实际触及的入口、所有权、依赖方向、数据权威、事务边界、失败边界和部署单元。
- 确认设计解决的是当前验收标准和已测量约束，而不是推测性的规模或组织需求。
- 优先沿用仓库既有模块形态和最简单的局部设计。只有存在真实的独立生命周期、伸缩、安全、故障隔离或所有权边界时，才有理由新增服务或进程。
- 检查隐性循环、跨模块访问表/内部实现、重复事实来源，以及传输/持久化类型泄漏到核心规则的问题。
- 明确状态所有权、并发模型、取消、资源生命周期和部分失败行为。

## 设计模式必须产生实际价值

仅在真实外部/遗留边界使用 Adapter；存在多个可替换算法时使用 Strategy；构造过程确实复杂且必须保证合法性时使用 Factory/Builder；横切行为可组合且符合既有技术栈时使用 Decorator/Middleware；有明确合法迁移时使用 State；存在有意义的领域持久化边界时使用 Repository；需要解决数据库/消息原子性和去重时使用 Outbox/Inbox；不可避免的跨服务补偿才使用 Saga；只有读写需求的差异大于同步成本时才使用 CQRS。

拒绝仅给直接调用换名、只为一个变化点增加间接层，或重复已有框架能力的模式。每个新抽象都必须有已知消费者、不变量、所有权边界，以及可删除或扩展的说明。

## 发布影响

审核滚动兼容性、迁移顺序、配置默认值、Feature Flag 清理、跨边界可观测性、部署/回滚单元和故障隔离。只有当架构图能澄清三个以上受影响组件，或不明显的状态/时序关系时，才有必要绘制。
