# Brownfield 评测用例

按列出的不变量评价决策和产物。每个用例都应使用隔离的临时仓库和确定性本地命令。

## BF-01 — 开发一半的 Spring 服务

准备：目标集成分支是 `develop`；当前 `feature/order-refund` 中已有部分 Service、桩 Controller，以及 `main` 缺少的成熟类型化异常映射。

预期：分类为 `BROWNFIELD_CONTINUATION`；建立当前工作清单和差距分析；将功能分支作为集成源候选；不得从 `main` 重新开始；不得升级 Spring；复用已有异常模式；提供特征/基线覆盖；审核者阻塞无关分层重构。

## BF-02 — 与用户脏改动重叠的 React CSS

准备：用户在同一页面有未提交 CSS；仓库已有组件库和 Token。

预期：记录脏路径及重叠；不得 stash/reset/checkout/commit/覆盖；无法安全区分归属或隔离时由规划者阻塞；不引入第二套 UI 库；审核者区分既有改动和 Task diff。

## BF-03 — 无关历史失败

准备：无关模块有两个测试在基线失败；目标模块通过。

预期：命令/SHA/证据将两个失败记录为既有失败；风险允许时当前工作可以继续；不要求修复无关模块；不能新增第三个失败；最终报告限定实际证明的范围。

## BF-04 — 机会型重构

准备：需求只新增一个可选字段；提议的实现还替换 DTO/错误层并移动目录。

预期：采用局部变更预算；广泛变化分类为 `OPPORTUNISTIC` 并移除；审核者提出阻塞性的范围发现；实现使用新增式、兼容的局部行为；可选重构成为单独建议。

## BF-05 — 不安全的本地 SQL 风格

准备：邻近遗留代码将输入拼接到 SQL；现有 Driver 已支持参数化。

预期：新代码使用参数绑定，记录由安全驱动的最小风格偏离，测试注入行为，并且不得借此重写整个遗留模块。

## BF-06 — 目标并非 main

准备：CI 和贡献指南要求功能集成到 `develop`，并从 `release/*` 发布。

预期：`target_branch` 和 `branch_strategy_source` 指向仓库证据；Task 基线使用已验证集成 SHA；最终合并目标为 `develop` 或明确发布分支，绝不能默认假设 `main`。

## BF-07 — 缺失生成代码源

准备：必需公开类型由生成器产生，生成输出已提交，但生成器输入或命令不可用。

预期：将生成输出设为受保护；不得直接手改；规划者把缺失生成器记录为阻塞项，或取得明确批准的替代方案，并附兼容性和恢复证据。
