# TEST_REVIEW（测试审核）

针对当前已批准 Spec 版本和变更风险，审核一个测试计划版本。不得编写测试或削弱预期。

## 可追溯性与层级

每个验收标准都必须映射到命名用例和证据。每个用例要说明前置条件、确定性数据、步骤/动作、预期可观察结果、清理、层级和自动化责任。选择最低且有效的层级；若真实边界使单元测试不足，则保留契约/集成/E2E 覆盖。

审核正常、非法、边界、部分失败、恢复、兼容性和回归路径。按适用性增加权限/租户、重复/幂等、并发/顺序、超时/取消/重试、迁移/回滚、浏览器/设备/可访问性/离线、安全滥用和性能/资源用例。

## Brownfield 证据

要求提供修改前完整 SHA 对应的基线命令、历史失败分类及证据、允许失败差异，以及对必须保持兼容的受影响行为进行特征化。不得固化明显缺陷或使用巨大快照。没有证明时，新增失败绝不能标记为既有失败。

## 确定性与诊断

检查隔离且不敏感的数据、受控时钟/随机数/网络、以有界等待代替 sleep、清理、可重复性、环境/版本记录，以及足以区分 Spec、测试、实现、环境和基线失败的证据。Mock 应位于真实外部或昂贵边界，而不是包围每个内部调用。

测试计划必须区分合成/Mock、本地真实边界、集成环境、live 服务和生产授权验证，说明每层能证明的行为、所需权限、不可用时的退出条件，以及哪些低层结果不能替代必需的高权威证据。优先在原计划中标记局部 BLOCKED 的环境切片，不要求每层测试成为新 Task；冻结后改图须由 Planner 提供必要性证据。不可拆分的必需验收条件缺失时，不得批准计划进入实现。

首次审核必须在同一轮完成全部适用测试维度并列出所有可识别的阻断 Finding。窄修正的增量复审应依据上一 Review、稳定 Finding ID、精确 Delta 和受影响场景逐项验证；测试层级、环境权威性或风险边界发生实质变化时执行完整复审。

确保 `not_run` 和退出标准明确。`PASS` 不能依赖 Skip、无限重试、弱化断言或未记录环境。只有计划能在指定风险级别证明期望行为与保持行为时，才可批准。

v2 测试计划使用固定 test-plan.md，当前阶段用例保持稳定 ID。仅职责/映射变化而 Oracle、层级、权限环境不变时，只复核相关映射与原批准适用性；不要求重新发布全部用例或哈希矩阵。测试预期变化不能伪装成映射调整。
