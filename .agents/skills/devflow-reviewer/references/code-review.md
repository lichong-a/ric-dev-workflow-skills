# CODE_REVIEW（代码审核）

针对 `base_sha..head_sha` 精确审核一个 Task 的完整候选，或其实现类/测试类 Defect 修正，并结合当前 Spec、测试计划、变更预算、仓库画像、各代码作者报告和已知基线。不得用分支名代替 SHA 进行审核。

## 确立 diff

验证两个 Commit 都存在，祖先关系/范围符合意图，报告文件与实际 diff 一致，既有脏改动未被包含或覆盖。将每个变更文件映射到 AC、必需风险控制、测试、迁移、文档或可观测性需求。无法合理映射的内容可能属于范围漂移。

Tester 可以按[测试代码交付](../../devflow-tester/references/test-code-delivery.md)提交原结构的 Implementation Report；核对真实作者、测试路径预算、预期与计划，不要求 Implementer 代写。多作者候选核对每份报告的原始范围、完整净差异和最终 head，不能修改旧报告绑定。G5 后测试代码变化同样需要新的代码审核；测试执行 PASS 或 G4 计划批准都不能替代它。

## 审核顺序

1. 正确性：完整 AC 行为、不变量、校验、null/空值/边界、失败/部分成功、资源生命周期、并发/顺序/幂等。
2. 安全/数据：认证与动作/资源/租户授权的区别；注入/XSS/CSRF/SSRF/路径/上传/反序列化/secret/隐私；约束、事务/锁、精度/时间、删除/审计、迁移安全。
3. 兼容性：API/DTO/事件/配置/错误/数据/枚举/序列化、旧调用方与客户端、滚动版本、默认/未知值和未声明行为。
4. 可靠性/性能：查询/网络瀑布、N+1、无界结果或 Task/内存、超时/取消/重试/退避、缓存/消息一致性和关闭。
5. 架构/维护：遵循仓库边界与模式，不引入虚假抽象/循环/框架替换，错误和清理清晰。
6. 可观测性/测试：结构化脱敏上下文、稳定指标/Trace/审计、真实行为覆盖、失败/竞争/回归用例和确定性测试。

只加载相关共享领域/语言参考。需要时检查生成 SQL/输出或运行只读检查，但不得修改被审核产物。“测试通过”不能证明未测试路径正确。

## Brownfield 预算

检查允许/受保护路径、依赖/锁文件、公开/数据变更、格式化半径、生成文件流程、参考模式一致性，以及重构属于 required/incidental/opportunistic 哪一类。除非能修复当前具体风险，否则广泛现代化不是发布要求，也不能被悄悄塞入 diff。

将结论绑定到 Task、Spec 版本和精确 SHA 范围。任何 head 变化都会使批准失效，除非新的明确范围审核覆盖该变化。
