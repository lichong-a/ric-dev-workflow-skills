# SPEC_REVIEW（规格审核）

审核一个精确 Spec 版本、Root Issue、适用时的 UI Spec、决策、变更预算和 Task DAG。

## 产品与行为

确认 Spec 解决原始问题，并分别说明当前、期望和保持不变的行为。范围/非目标必须防止悄悄扩张。每个验收标准都必须可观察、无歧义、可独立测试，并覆盖重要失败/恢复和边界行为。

检查用户流程，以及适用的 API/事件/配置、数据/迁移、权限/租户、稳定错误、兼容性/滚动版本、安全/隐私、性能/可靠性、可观测性、部署和回滚。重要假设需要证据或阻塞问题。不得为填补缺口而虚构产品行为。

对于 UI，验证复用现有组件、Token 和交互，并按相关性定义加载、空数据、错误、成功、禁用、无权限、离线、响应式、可访问性、长文本/极端内容和国际化行为。

## Brownfield 与设计

确认 Spec 保持未声明的公开/隐含行为，处于保守变更预算内，并沿用仓库模式。安全或正确性所必需的偏离必须局部且有说明。拒绝推测性服务、框架升级、依赖替换、大范围重命名，以及没有真实变化/失败/所有权边界的模式。

## DAG

检查所有 AC 和必需风险控制均映射到 Task；Task 单一职责、可独立审核/测试、无环，并包含依赖、基线策略、允许/受保护路径、参考、交付物、验证和风险。共享契约、数据库、构建或写区域必须串行。

检查会改变 Spec、测试或 Task 边界的可发现事实已经在正式送审前完成预检。若请求实质上包含多个可独立交付阶段、不同发布/权限/环境边界或无法形成紧凑审核包，确认规划者已保留完整能力清单并在 G2 前合理分期；不得接受通过缩小当前 Spec 隐藏原始目标，也不得强行拆分不可独立验收的原子行为。

目标仓库存在既有交付协议时，确认等价证据的语义范围、独立所有者、版本/SHA 和时效性确实满足对应 Gate；不得要求复制同一事实，也不得用较弱的本地流程覆盖更严格的仓库规则。

## 完整审核与复审

首次审核必须完成全部适用维度，并在同一轮列出当时可识别的全部阻断 Finding。增量复审必须读取上一 Review、稳定 Finding ID、精确 Delta 和受影响邻域，逐项确认关闭证据；若修订改变行为、架构或风险边界，则转为完整复审。不得仅因发现第一个缺陷就提前结束可继续进行的审核。

`APPROVE` 只绑定当前 Spec 版本。产品行为此后仍需用户批准。行为缺失、不安全兼容性、不可测试标准、范围漂移或无效 DAG，应产生带具体位置的 `REQUEST_CHANGES`。

v2 以 current 中对象独立修订为单位。仅预算/依赖变动时检查相关 Task、边和限制；未变行为不要求重新用户批准或重发所有 Task。任何适用性沿用须绑定旧/新身份与 Delta，不得仅凭父文件版本相同或不同推定通过/失效。推测性优化不作为当前阻断项。
