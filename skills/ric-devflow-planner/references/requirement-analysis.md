# 需求分析与规格说明

完成需求接收并掌握仓库上下文后，使用本参考。

## 交付分类

必须且只能设置一个主要工作类型：`feature`、`continuation`、`bugfix`、`migration`、`refactor`、`maintenance` 或 `infrastructure`。只有用户明确要求时才使用 `refactor`。即使一个功能需要大量清理，也不代表清理自然属于该功能范围。

无公开契约影响的局部低风险变更使用 `FAST`；普通多文件/模块工作使用 `STANDARD`；认证、授权、租户、支付/金融/隐私、破坏性数据/迁移、公开 API/事件、一致性/并发、生产基础设施、安全或广泛兼容性相关工作使用 `HIGH_RISK`。事实显示风险时应提升深度；不得只为节省时间而降级。

## 构建行为契约

先描述问题和期望用户价值，再明确划分：

- 由代码、测试或运行时验证的当前行为；
- 本请求要改变的期望行为；
- 必须保持的行为，包括未明说的 API/数据/事件/配置/错误/UI/权限/可观测性预期；
- 非目标和授权边界。

验收标准应写成可独立观察的结果，包括前置条件、动作/输入、预期输出/状态/副作用，以及失败/恢复行为。分配稳定的 `AC-NNN` ID。除非行为本身就是工程契约，否则避免只描述实现方式。

按适用性定义用户流程、业务不变量、API/事件/配置、数据与迁移、权限/租户、稳定错误、兼容性、安全/隐私、性能/可靠性、可观测性、UI 状态、部署顺序、回滚、假设、风险和开放问题。只有确定实际技术栈或边界后，才加载相应共享领域/语言参考。

对于 UI 工作，先盘点现有设计系统原语和相邻流程，再覆盖加载、空数据、错误、成功、禁用、无权限、离线、响应式、键盘/焦点/辅助技术、长文本/极端内容、i18n 和受保护 UI 区域。不得引入平行视觉体系。

## 正式门禁前事实预检

在第一次 `SPEC_REVIEW` 前，使用有界只读侦察解决会改变 Spec、测试计划或 Task 边界的可发现事实。按相关性核对仓库规则与真实入口、依赖和生成器版本、数据/供应商能力、安全与权限边界、可执行验证命令、环境可用性及当前授权。预检深度与风险和不确定性相称；不得为了形式扫描无关仓库区域。

能够从源码、配置、锁文件、CI、契约或安全本地探针取得的事实，不得作为开放问题交给 Reviewer 逐轮发现。无法验证的事项必须明确标为假设、受影响验证切片或阻塞项，并说明证据所有者和解除条件；不得虚构默认行为。

## 规模、分期与完整范围

默认一个 Root 的完整交付结果。仅当多项能力确有独立发布/验收边界或当前无法共同验收时，在首次 G2 前做一次有依据的分期；优先同一 Root 记录阶段，需要独立跟踪时才另建 Root。交接长度、技术层数量或预估耗时不构成拆分理由。使用现有 Root Issue/Decision 文本保留完整能力清单、当前阶段、延期项、跨阶段依赖和最终完成条件；v2 使用 current 中现有章节，不递归为阶段建立规划树。

拆分不得隐藏、删除或默认取消原始目标。每个阶段必须说明它独立交付的价值以及不包含哪些后续能力。若行为必须作为一个原子事务或一次兼容切换才能验收，则保持单一 Root Issue，不按文件、技术层或任意数量阈值强行拆分。

测试、可恢复性和安全约束只覆盖当前 AC 及其真实边界；不自动加入用户未要求的管理平台、通用框架、额外服务或未来能力。机会性建议记入延期，不自动成为当前 DAG 的节点或阻断依赖。当前阶段 DAG 冻结后按任务参考的例外入口处理，不能把实现细节不断转化为新需求。

## 目标仓库协议映射

识别目标仓库已有的 Issue、设计、测试、CI、发布、审批和状态事实，并在仓库画像现有章节中记录它们与 G0–G10 的映射。仅当语义范围、独立决策所有者、版本/SHA 绑定和时效性等价时，才复用已有证据；状态引用原始路径或身份，不复制同一内容。规则不等价或冲突时采用更严格的一项，并记录原因。

## 可审核条件

当以下条件全部满足时，Spec 才可进入审核：范围和非目标无歧义；每个 AC 可测试；保持行为和兼容性明确；重要决策包含证据和备选；Brownfield 预算保守；会改变设计边界的可发现事实已完成预检；交付阶段可以独立审核；无需虚构产品行为即可推导 Task；开放问题已解决或记录为阻塞项。送审前继续在草稿中修订，不得用连续正式版本代替自检和事实侦察。

当前阶段决定所需事实已经足够时停止调查。默认一次聚焦侦察和一次缺口补查；连续两次同类搜索没有新事实则停止。必须进一步验证的缺口明确关联 AC/失败/必要约束，其他建议记入延期项，不能以“还有优化空间”延长正式送审前准备。
