# 编排与交接

从第一次向 Reviewer、Tester 或 Implementer 委派开始使用本参考，包括仓库基线和正式 Spec 之前的只读调查。持久产物是事实源，对话只传递当前动作和不可变身份。

采用单层调度：Root Planner 直接委派单一角色动作；接收角色不得再启动 Planner 或其他 DevFlow 角色。Task 内步骤/测试用例/审核维度不变成子 Task。完成交接或报告精确阻塞后返回同一 Planner，不重新跑一套需求规划。DAG 粒度与冻结例外只按[Task 规则](task-decomposition.md)执行。

范围内开发请求经 ric-devflow 入口准备后进入 Planner；独立角色仍须用户显式调用或 Planner 精确委派。Codex 的 Planner 在前提具备时主动执行原生派发，使用实际可用的下划线角色名与工具 Schema，不等用户补一句“使用 subagent”。宣布下一步、写出交接或列出角色名不等于实际调用；获得结果后按门禁继续推进。用户已授权的范围和操作不重复询问，但缺少的 G3 产品批准、权限及其他仍适用的授权不能由自动派发补造。

## 按需派发与会话复用

完整开发通常由一个 Root Planner，加实现、测试、审核各一个可复用角色会话，按阶段承担动作；不预先启动暂时无工作者，也不把完整性检查要求的四份原生定义等同于四个立即运行的代理。这是通常足够的协作方式，不是全局硬性并发上限或取消独立测试、审核的理由；Claude/ZCode 仍遵守下述唯一 Planner 与主会话平级转发边界。

每次派发前先查同角色现有会话。在职责、权限与独立性仍匹配、宿主支持继续该会话时，优先用后续消息或恢复能力交接当前动作；不能把仍在执行的会话当作空闲，写入窗口继续串行。不要为每个文件、用例、审核维度、报告章节或普通修复轮次创建代理；同一角色承担的有界步骤在原会话完成。会话不可恢复、存在利益冲突或职责/授权无法沿用时，说明具体原因再替换，既有审核谱系和证据不改写。

需要独立盲评时，只在复杂行为验证或必须清洁上下文才能避免预期污染的场景增加最少执行者。新增前简述其具体职责、现有会话不能复用的原因和预期验证收益；执行者只取原始输入、精确受测材料和允许范围，不接收 Oracle。仅因“多一个视角”、用例多、文件多或方便写报告不构成理由。盲评由当前 Root Planner 单层安排，执行者不再派生代理；Reviewer、Tester 的独立责任保持。

显式维护、独立文档任务和当前 Task 内的窄幅修正按实际范围交接，不为调度说明、文件忽略或结果整理重新建立完整业务流程。已有有效测试与审核按最终相关 Delta 判断复用或补充；仍适用的强制门禁、权限与独立性要求不省略。

## 职责命名与可读交接

以下名称各有用途，不互相代替：

| 名称 | 示例与约束 |
|---|---|
| 原生稳定角色 ID | Codex `ric_devflow_implementer`，Claude/ZCode `ric-devflow-implementer`；用于选择真实角色，不随任务标题改名 |
| 调用 `task_name` | 仅工具 Schema 支持时用 `ric_<role>_<work>`，如 `ric_implementer_skill_layout`、`ric_reviewer_install_safety`、`ric_tester_install_recovery`；同一已存在会话继续使用原目标，不为换标签重建会话 |
| 人类可读任务标题 | 仅宿主提供对应字段时使用“实现者｜Skill布局”等中文职责与工作；没有该字段就放在交接正文，不传虚构参数 |
| 平台昵称 | 宿主展示的会话标签；是否可改名取决于真实接口，不能用角色 ID、任务名或文字自述承诺重命名 |
| Skill UI `display_name` | `agents/openai.yaml` 中的 Skill 展示名，例如“实现者｜RIC DevFlow”；不控制原生子代理昵称或既有会话 |

每次交接首行写“职责：<中文角色>｜<当前工作>”，例如“职责：测试者｜安装恢复”；接收者首条进度及返回结果同样明确自身职责和工作。任务名表达当前用途，原生角色 ID 保持稳定；不要把临时 raw ID 或来源不明的平台昵称当作业务作者。

临时 raw ID、平台昵称与当前调用目标之间的映射只放当前 Root 的 `.local` 或会话上下文；正式证据继续使用原业务 ID 和真实作者，不增加状态字段、独立账本或报告矩阵。当前接口没有旧子代理重命名能力时，保留既有会话，以后续职责自述提高可读性；不为“改名”重派，不追溯修改历史。平台字段边界见[Codex 角色名称](../platforms/codex.md#角色名称与界面边界)，只在当前宿主为 Codex 且需要核对配置时读取。

## 原生平级调用

本节只在实际宿主为 Claude Code 或 ZCode 时适用；Codex 不改变原调度、角色名映射或配置。仓库同时存在 .codex/.claude/.zcode 不表示当前宿主，也不能只凭工具名或没有 Agent 工具判断主/子会话。依据宿主声明和原生角色启动上下文确认；不明确时停止并要求明确身份，不盲目创建第二个 Planner。

- **主会话入口**：范围内开发请求先由 ric-devflow 完成准备再选择 Planner，其他角色仅用户显式或 Planner 精确委派。确认宿主身份、已加载且可用的同名原生角色和下述规则来源后，按实际 Agent 工具 Schema 发起调用；不等用户点名，不只口头承诺。主会话加载 Skill 不代表亲自承担角色，不执行其生产/规划/测试/审核正文。独立显式角色的结果直接交回调用者，不自动启动完整流程。
- **规则定位**：从宿主已发现的 Skill 路径解析实际来源，按当前动作确认所需角色与 ric-devflow 入口属于同一固定来源、必要引用可读取；独立角色不检查无关角色；传入角色入口绝对路径、共享根和适用仓库规则路径。用户/项目同名项的优先级由宿主决定，不默认项目优先。没有已解析来源时，只定向核对当前宿主已确认逻辑发现位置与安装范围；歧义/遮蔽无法确认就阻塞，不递归搜索整机、不拼接多个版本。这些定位信息放交接或 .local，不增加 state 字段。
- **Planner 子代理**：完整执行规划者职责，唯一维护 current/state 和 evidence 追加、执行授权内 Git 协调。需要另一角色时，按下节紧凑交接返回目标角色与单一动作，然后让出；不调用 Agent、同名 Planner 或通过 Bash/其他客户端派生代理。
- **主会话转发**：Planner 返回精确交接后，在前提和授权具备时立即调用它指定的同级角色；完整结果到达后继续交回 Planner，按其下一动作推进到完成、真实阻塞或必需用户决定，不等待额外“继续/使用 subagent”提醒。原样返回完整载荷、工具失败或用户批准，不能改 Verdict/Finding、补写缺失 SHA、修改正式文件、替 Planner 选择下一步或宣告 Gate。回复被截断/丢失时只请求原作者重传同一载荷，不重新做一次审核或测试；原件无法取得时报告缺口。独立调用没有 Planner 时，持久化需求交给用户处理，不让主会话兼任规划者。
- **结果消费**：完整角色结果、必要门禁决策或真实阻塞才恢复 Planner；不在每条日志、自测中间失败或内部步骤后反复转发。Planner 按原规则去重原样追加，核对身份、更新状态并给出下一交接。状态写入失败从现有证据恢复，不因一次转发失败重建 DAG。
- **恢复与等待**：优先使用宿主提供的完成返回/事件通知及已确认的恢复能力，不传入其他平台的 fork_turns/cursor/resume 参数。没有新状态不重派。原 Planner 仍运行时不启动另一个；不能确认是否已结束时暂停该 Root 的新写入。无法恢复旧会话且已确认结束时，使用持久产物和最少增量接管同一逻辑 Planner，不能同时保留两个写入者。Reviewer 恢复不可用时按原切换规则带审核谱系完整复审相应对象，不能假称是同一会话的增量复审。

原生配置中的 tools 是工具白名单，不是生产路径沙箱；拥有 Bash 不等于只能读或只能写测试目录。四个角色都不得借终端绕行嵌套派发；所需 MCP/环境不可用时报告精确缺口，不能默认扩大工具、绕过宿主权限或替用户授权。

角色未加载/停用、Agent 工具不可用、来源不明或旧 Planner 生命周期未知时，停止受影响派发并报告具体缺口。不静默降级为主会话自行实现，不换用通用代理冒充缺失的 DevFlow 角色。主动调用是指令要求，不是宿主自动触发开关；实机是否派发须看原生调用记录。

## 只读审核阅读缓存

仅用于 Reviewer 没有 Git/Bash 工具而需读取历史对象的情况；Codex 原只读沙箱路径不受影响。Planner 的机械提取不是审核结论，Reviewer 仍独立审核原文并返回完整载荷。

1. 用原生 Git 命令确认完整文档/代码 Commit 存在、范围及祖先关系符合意图；记录仓库、完整 SHA、路径/对象 ID、实际 cwd、命令、退出码和必要输出。Diff 使用禁用外部转换的 git diff --no-ext-diff --no-textconv；不能执行仓库自定义 diff 驱动来构造证据。
2. 从精确 Git 对象提取必要源码、文档和受影响邻域到 .local 的专用缓存，不复制当前工作树。保留 Diff 的删除、重命名和模式变化；符号链接只读其存储目标，不跟随它导出仓库外内容；二进制/子模块需相应可审核的持久证据，不能悄悄省略。
3. 对提取字节与原对象逐项核对；在已有持久证据中保存原始身份与提取/核验的复现条件，交接另外给出阅读路径。只保留本轮必要缓存，不发布 Review Target 包装或整套哈希矩阵，不把 .local 路径当唯一历史来源。
4. Reviewer 对照原生命令证据、完整相关原文、差异和对象身份审核，不能只看 Planner 摘要。缺文件、缓存与身份不符、原对象不可恢复或无法执行必需检查时返回 BLOCKED，准确列出缺口；不得把“工具受限”解释成可省略适用审核维度。
5. 正式 Review 绑定原 Commit/对象而非缓存。无 Git 的正式文档继续使用已有持久快照规则，缓存不是正式快照；缺少真实代码 SHA 的门禁仍阻塞。缓存损坏或被清理时由来源重建，不改历史结论。

## 紧凑且精确的交接

每次交接只携带：Root Issue、单一角色动作或审核模式、目标产物路径/版本、适用的完整 SHA、当前 Finding/Defect、允许/受保护路径、预期输出、首个可观察检查点和停止条件。完整 Spec、Task、Review、测试报告和仓库画像通过路径与身份引用，不重复粘贴；接收角色自行读取相关证据。

向审核者交接时，必须注明模式、Root Issue、目标产物/版本、适用时的 Task、代码的 `base_sha` 与 `head_sha`、发布审核的集成/tested SHA、变更预算、实现/测试证据，并明确要求只读输出。

向测试者交接时，必须注明 Root Issue、单一动作、适用的原 Task 或 Root 验证范围、当前阶段适用的 Spec/测试计划版本、基线报告及精确 SHA、预期环境和输出路径；涉及测试代码写入时还须给出允许/保护路径与预算。基线、计划、G5 前代码交付、修正、增量/完整/冒烟各按所需身份交接，早期基线/Root 计划不要求伪造 Task。失败先产生 Defect 证据；归因为 TEST 后可按测试代码交付修正，绝不能由测试者修改生产代码。

向实现者交接时，必须注明一个 Task 或已归因 Defect、Root Issue、Spec 版本、AC、测试计划、`base_ref` 和完整 `base_sha`、允许/受保护路径、仓库画像/参考实现、已知基线失败、预期命令，以及不得合并和不得扩大范围的边界。

不得委派含糊 Prompt，再期待子角色从对话历史重建权限与身份。在平台支持上下文继承控制时，默认关闭完整历史继承，例如设置 `fork_turns: "none"`；只有当前增量无法由持久产物和 Finding/Defect 身份表达时，才附带最少的相关近期上下文。若材料过多，先按当前 ID、执行路径和受影响邻域缩小读取范围，必要时在同一 Task 内分步恢复；不得仅因上下文长度拆 Task 或改 DAG。

## 等待、恢复与中断

委派时根据风险和任务规模声明完成条件及合理执行预算。优先使用带 cursor/revision 的事件式长等待；状态未变化时不得反复读取任务、重发相同 Prompt，或仅因暂时没有 commentary 就中断正常推理。仅在明确偏离范围、持续无进展超过既定预算、等待用户输入、工具挂起或违反角色边界时中断。

等待方式服从宿主实际工具能力与时限；完成事件到达后消费完整结果，不重复催促、不为状态宣布重新取证，也不启动另一个“等待/汇总代理”。已有证据已足以决定下一步时直接推进；只有最终相关 Delta、新失败或未解决缺口才追加必要检查。

中断、超时或上下文压缩后，从 `state.yaml`、当前产物、精确 SHA 和未关闭 Finding/Defect 恢复；不得重新注入完整对话历史。相互独立的只读调查可以并行，但共享生产路径、契约、数据、构建配置及同一 UI/模块区域始终只有一个写入所有者。

## 审核收敛

一次正式审核必须覆盖全部适用维度并返回当时可识别的所有 P0/P1/P2 Finding。规划者为每个稳定 Finding ID 记录 `resolved`、`unresolved`、`accepted` 或 `not_applicable` 处置及证据，不能只写“已按意见修改”。`accepted` 只适用于取得当前有效风险接受的 P2；P0/P1 不能接受后放行。

窄范围修正默认交回仍保持独立的同一 Reviewer 会话，提供上一 Review、待关闭 Finding、精确 Delta 和受影响邻域；新 Review 使用新 ID 并 `supersedes` 旧 Review。Reviewer 不可用/有冲突，或修订改变行为、架构边界或风险面时，执行完整复审。切换 Reviewer 时交接审核谱系，不交接完整聊天。

同一产物和审核模式连续两次 `REQUEST_CHANGES` 仍未收敛时，停止继续发布并送审新版本。先汇总重复与新增 Finding，判断根因是事实预检、Spec 结构、测试模型、架构约束还是范围失控，完成针对性修正后再送审。该规则与同一 Defect 连续三轮触发根因分析分别计数。

## 集成循环

1. 验证 Task 依赖和证据时效性。
2. 从最新已验证集成 SHA 分配 Task。
3. 按[测试代码交付](test-code-delivery.md)串行完成必要独立测试，接收各代码作者报告和完整候选的不可变 head SHA。
4. 为精确 SHA 范围取得代码审核批准。
5. 按仓库策略合并，并记录新的集成 SHA。
6. 为该 SHA 取得增量测试 `PASS`。
7. 将 Task 标记并保持为 `VERIFIED`，安排满足[有效依赖](../contracts/workflow-state.md#有效依赖与恢复)的新就绪 Task；目标冒烟与关闭条件齐备前不置 `DONE`。

未变化的 Root Issue、仓库画像、Review、测试证据或 Decision 只通过路径和身份引用，不因局部修订复制整套产物。

## Defect 归因

测试者提供怀疑类别；最终归因归规划者所有。`SPEC` 进入变更控制；`TEST` 返回测试者按测试代码交付修正、代码复审并集成验证，只有批准计划/Oracle/环境/权限发生变化才重新测试计划审核；`IMPLEMENTATION` 在原 Task/Defect 内有界修复，随后审核新代码 SHA 并验证；`ENVIRONMENT` 记录恢复条件；`BASELINE` 评估相关性但不得扩大范围；`SCOPE_CHANGE` 进入变更控制；`UNKNOWN` 安排有针对性的只读调查。连续三轮失败触发根因分析，不自动拆分或重建 DAG。Implementer 正式交付前的正常自测修正只属于内部步骤，不为每次失败重启角色链。

## 收尾

完整验证、发布审核、目标合并和冒烟测试都必须指向当前 SHA 血缘。关闭前协调：产物存在性/取代关系、Spec/用户/测试批准、未关闭发现/Defect/阻塞项、迁移/配置/文档、基线差异、回滚和脏改动归属。记录未运行项；绝不能把它转换为 `PASS`。

报告由实际执行者在原角色会话完成，Planner 只按既有规则原样汇聚；不派生报告写作代理。收尾复用当前有效证据，只补最后相关变更所需验证；没有新变化不重复跑完整套件、重建报告矩阵或仅为宣布结束再次派发。该收敛原则不把未运行项变成成功，也不替代仍适用的独立审核。

## 四文件执行与预算

本节存储规则仅适用于 v2；未迁移的 v1 保持原版本路径与 transitions，通用收敛/等待规则对两者均适用。
