# 设计模式参考与模块化设计

Planner 在形成 Spec／设计决策前、Implementer 在开始本 Task／实现类 Defect 的设计与实现前读取本参考。工程级和代码级都应在当前需求、既有架构与批准预算内尽量解耦、模块化；具体模式必须解决真实问题。

## 本地技能检测与必需参考

1. 优先从宿主提供的技能清单和已解析路径定位 `ric-design-patterns-skill`；必要时，只定向检查当前宿主已确认的项目级、用户级技能发现位置。不得扫描整机、硬编码本机目录或猜测另一宿主的安装路径。
2. 同名项按宿主已确认的有效来源解析，不自行假定项目级或用户级优先。来源有歧义时报告候选与缺口，不拼接多个版本、不擅自选一个继续。发现位置尚未确认或无法检查时，记录“检测未完成”，不能记为“未发现”。
3. **发现可用的本地技能后，必须实际读取其 `SKILL.md`，再完成设计或实现决策。** 按该技能指引，从当前语言和真实变化点出发，按需读取语言索引及相关模式详页；不预加载全部语言和模式。没有适用语言或 GoF 问题时说明不适用，仍执行下文设计原则。
4. 同一角色会话中，同一来源、内容未变的已读材料可以复用；来源或内容变化时重新读取受影响材料。Planner 的读取记录和交接不能替代 Implementer 自身读取，不得把路径存在或他人已读声称为本角色已参考。
5. 在已确认发现范围内未发现该技能时，记录检查范围与结果并继续任务；不自动安装、下载或复制。已发现但入口或当前决策必需页面无法读取、来源有歧义或存在明确禁用时，报告精确缺口，暂停依赖该参考的设计结论及实现，继续不受影响的工作；不绕过权限、反转禁用或伪称已参考。

外部技能仅提供条件性的设计参考，不属于 DevFlow 五 Skill 的安装闭包，也不增加角色、权限、批准或 Gate。它的建议不能扩大已批准任务，不能替代当前仓库指引和角色契约。

## Planner：工程级职责与依赖

- 在受影响范围内明确模块职责、公开接口、依赖方向，以及数据、状态、外部系统和副作用的所有权边界；按需标明可替换部分和验证边界。
- 优先沿用稳定模块，减少循环依赖、跨模块访问内部实现、重复事实来源，以及传输或持久化细节向核心规则的泄漏。保留必要的业务内聚，模块数量不作为质量指标。
- 从直接使用现有能力的基线出发，比较解决当前变化点所需的最少方案，说明收益、复杂度和兼容性代价。模块划分不自动拆成 Task 或服务，既有单层调度与冻结 DAG 规则继续适用。
- 将检测结果、实际读取的来源与相关页面、变化点、方案取舍及采用或不采用模式的理由记入现有 Spec／Decision 内容，并随 Task 交接。v2 使用 current 的现有章节；v1 使用原版本路径，不新增状态或 Schema 字段。

## Implementer：代码级职责与边界

- 先核对本角色读取的参考与 Planner 交接的设计决策，在已批准 Spec、Task 和预算内实现；新的参考建议不构成重写批准设计的授权。
- 保持函数、类和模块职责集中，封装内部状态及不变量；通过必要的接口、组合、参数传入或语言惯用机制隔离外部依赖和可替换行为，保留可测试边界。优先复用现有抽象，不要求每个类或调用点新增接口。
- 自审本次新增的依赖方向、跨模块内部访问、共享状态和既有调用方影响，并以相关行为及回归验证支持边界保持。必要解耦超出公开契约、允许路径或预算时，交回 Planner 处理变更控制。
- 在实现报告现有 `design_decisions` 中记录检测／读取结果、实际来源、采用或不采用模式的理由，以及与规划决策的关系；`reused_existing_patterns` 只记录实际复用的既有模式，没有复用时保持空列表。保持原报告字段和不可变发布规则。

## 模式取舍与最小变更

参考是必需动作，采用具体模式取决于真实收益。按[架构审核](architecture-review.md)判断新增抽象的价值，按[最小完整变更](minimal-change.md)保持范围。简单修复、纯指令编辑或无适用模式时，明确选择直接、局部的方案即可；不得为了证明“用了技能”增加层次、通用框架、依赖、服务或机会性重构，也不得把分布式架构问题强行套入 GoF。
