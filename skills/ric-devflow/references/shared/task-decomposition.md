# Task 粒度与冻结 DAG

只有在 Spec 与变更预算自洽后，才创建当前阶段的最小交付 DAG。默认从一个完整纵向 Task 开始；只有真实依赖、独立发布/验收或不可合并的写入/权限边界，才增加正式节点。Task 数量不是规划质量指标。

## Task 质量

每个 Task 承担一个完整交付结果，可以覆盖多个关联 AC 和实现步骤，并包含：稳定 ID/标题、当前 Spec 版本、AC ID、依赖、`latest_verified_integration_sha` 基线策略、允许/受保护路径、相近参考实现、预期交付物、验证预期、风险，以及适用时的明确非范围。正式 Task 必须可以独立实现、审核和测试，不能暗中完成第二个交付结果。

按稳定所有权或依赖边界拆分，不能机械按文件或技术层拆分。如果把 Controller/Service/Data 拆开会导致任何部分都无法独立产生意义，则保持纵向切片完整。只有上线或兼容性要求顺序时，才优先拆出迁移/契约 Task。

## 实现步骤不升级为任务

接口接线、数据校验、异常处理、单元测试、生成物和必要文档通常是同一 Task 的内部清单，由 Implementer 分步完成并自测。步骤可以调整顺序、增加检查点或分次提交（须有授权），但不分配新 Task/Root ID、不进入 state、不建立子 DAG，也不逐步骤重新走 G0–G4 或独立代码审核。最终完整候选再走该 Task 的 G5/G6。

测试、审核、侦察、交接和记账是角色动作，不为凑流程各建一个 DAG 节点。只有用户本身要求独立交付测试基础设施、审计报告等，或存在不能合并的真实交付边界时，才成为 Task。只读侦察助手不是新的交付任务；子角色不得递归委派其他 DevFlow 角色。

## Root Issue、阶段与环境边界

Task 只表达当前交付阶段内的工作。仅在首次 G2 前，对确有独立交付/发布边界或当前不可共同验收的 Program 做一次分期，默认在同一 Root 保留完整能力清单和后续阶段；独立跟踪确有必要时才建立其他 Root。多文件、多个技术层、预估耗时或较长材料本身不是分期理由。跨阶段关系通过现有 Root Issue/Decision 文本引用，不改变 Task Schema；不能递归为阶段再创建完整规划树。

区分合成/Mock、本地真实边界、集成环境、live 服务和生产授权验证。优先在测试计划内区分验证切片，不因每一层测试自动新增 Task；只有确需独立调度/验收时，才在初始规划中分开。冻结后新发现环境缺口按下节判断，只阻塞受影响部分；若 Task 必需 AC 依赖当前不可获得的权限或环境，该 Task 不得 READY/VERIFIED，不得以较低权威结果替代。

## DAG 冻结与唯一例外入口

首次规划完成即固定节点 ID、职责和依赖作为送审基线；G2 通过后冻结。G4 细化测试用例、执行进度、内部清单、自测返修、上下文压缩或更换执行会话均不改图。流程动作/检查点不要画成正式依赖节点；只有一项 Task 时用列表即可，不强制绘制图形。

只有已观察证据证明原 DAG 无法安全或正确完成当前批准 AC 时，Planner 才可提出局部结构变更：用户明确改变范围；必要依赖错误/成环；无法在现有 Task 内解决的安全、权限、环境、发布顺序或写入所有权冲突。先判断原 Task 内分步执行、局部预算修订或阻塞记录是否足够；“可能更清晰/更并行”、工作较慢、材料太长、普通 Defect 或审核建议不满足例外。

例外使用已有 Decision/Change Log，记录具体 AC/失败证据、不改图为何不可行、旧/新节点与边、受影响批准和最小修正；不新增申请文件。结构变化须 G2 局部技术复审；行为/权限/测试预期改变仍重开受影响 G2/G3/G4 并取得所需用户批准。保留未变 ID/边/批准，禁止全图重建、重编号或借拆分重置 Defect/Finding 计数。证据不足时保留原图，必要处 BLOCKED。

## DAG 检查

- Spec 中每个验收标准都映射到一个或多个 Task，随后还要映射到测试用例。
- 每个 Task 都必须贡献于某个 AC、必需风险控制、迁移、文档或验证结果。
- 依赖必须必要且无环；通过拓扑排序确认。
- Task 不能依赖会移动的分支。只有进入 `READY` 时才设置具体 `base_ref`/`base_sha`。
- 修改共享公开契约、数据库对象、构建文件、共享配置或同一 UI/模块区域的 Task 应串行执行，除非能证明所有权互不重叠。
- 生成产物必须注明生成器源和命令。
- Brownfield Task 必须留在已批准变更预算内。潜在清理记入延期，不自动创建后续 Task，更不能作为隐藏依赖。
- Task 的验证预期必须注明实际环境层级、所需授权、可用性证据和更低层结果不能证明的事项。

## 就绪条件

只有满足以下全部条件时才标记 `READY`：所有依赖满足[有效依赖](../contracts/workflow-state.md#有效依赖与恢复)（有有效证据的 `VERIFIED` 或已完整关闭的 `DONE`）；Spec/测试批准仍为当前有效；最新集成 SHA 已知且干净；worktree 隔离安全；允许/受保护路径精确；本 Task 必需的环境和权限已具备；每个写入窗口只有一名代码作者。否则保持 `PLANNED`，或带原因标记为 `BLOCKED`。原 Task 内 Implementer 与 Tester 的串行交接不构成新的 DAG 节点。

## 独立修订与完整交付预算

v2 每个 Task 在 current 中使用稳定 ID 和独立 revision，仅受影响对象更新；当前状态由 state 索引，不能复制 Task 全文进去。Task 的 spec_version 表示实际批准的行为基线，父文档其他章节变更不要求机械换号，沿用按变更控制提供适用性依据。

预算包含测试、生成物、必要文档和余量；宿主定义了行数/字节硬限制时沿用其计数口径。未定义时不另造全局硬阈值。预算不足先处理原 Task 的有界预算修订，不默认拆 Task；依赖调整必须先满足冻结例外，再作局部技术复审。不把所有 Task 复制到 tasks-v*，不重建无关计划。
