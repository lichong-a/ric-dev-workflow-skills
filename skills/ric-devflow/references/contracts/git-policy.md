# Git、worktree 与并发策略

准备或恢复 Git 工作区、固定代码身份、集成或回收工作区时读取本契约的对应章节；仅导航到本文件不要求立即执行这些动作。

## 仓库事实优先

规划者按以下优先顺序确定目标分支和合并策略：用户明确指示、贡献指南、CI 触发规则、近期同类变更、upstream 跟踪关系，以及当前功能/发布实践。绝不能默认假设为 `main`。

记录：

```yaml
target_branch: ""
target_base_sha: ""
integration_branch: ""
integration_base_sha: ""
branch_strategy_source: ""
```

如果仍不能安全确定目标，应阻塞并询问用户。

## 单功能分支与不可变基线

- 每个 Root 默认只使用一个功能分支承担集成，`integration_branch` 即该功能分支，不另建 integration 分支。优先复用用户指定或已确认的当前功能分支；确需创建时基于实际目标分支，遵循仓库命名规范，无规范时使用 `feature/<REQ-ID>`。目标分支与功能分支语义不同，不能为了复用而把目标分支直接认作本次功能分支。
- 所有依赖满足[有效依赖](workflow-state.md#有效依赖与恢复)（有有效证据的 `VERIFIED` 或 `DONE`）后，Task 从最新已验证集成 SHA 开始；`base_ref` 记录来源功能分支，`base_sha` 固定真实基线，不新增 Task 分支或工作区状态字段。
- 仅为已就绪且需要写入的 Task 按需创建隔离工作区：由 Planner 使用 `git worktree add --detach <path> <base_sha>`。必须显式给出 `--detach` 和精确提交；不得省略提交参数、使用 `-b/-B` 生成默认 Task 分支，或强行让多个 worktree checkout 同一功能分支。无 Git 时继续既有快照流程，不模拟 Git 身份。
- 实现者、测试者绝不自行合并。Planner 在授权内按 DAG 顺序和仓库既有策略集成获批候选；无约定时能快进则快进，否则普通 merge 保留候选血缘，每次集成后对新 SHA 触发增量测试。冲突代码由对应原作者在串行窗口修正，Planner 不代写；新候选必须重新取得适用代码审核与测试证据，不能把解决冲突后的 SHA 冒充先前获批候选。
- 单功能分支不扩大 Git 权限；不得强推或重写共享历史，也不自动删除业务仓库已有分支或迁移既有 Root。

## 候选身份核验

代码审核读取本节即可核对 Git 身份，不为审核提前加载工作区创建、保全或回收流程；只有受审对象本身涉及这些行为时再读对应章节。审核真实的 `base_sha..head_sha`，而不是会移动的分支标签；detached HEAD 是 Task 工作区的正常状态。核实 Commit 存在、父提交/祖先关系及实际差异，`base_ref` 只是来源提示，分支名不能替代 SHA 证据。保留原作者报告的真实范围，不能把工作区叠加内容或后续提交冒充受审候选；缺少身份或必要读取条件时返回精确缺口。

## worktree 交接、复用与保全

- 同一 Task 默认复用一个 detached worktree，生产实现、独立测试代码及普通返修由各自作者串行交接；不为角色切换、测试或修复轮次新增分支/worktree。只读审核读取精确对象，不因审核另建写入工作区。
- 派发时在会话/工具参数中给出实际工作区、`base_ref`、完整 `base_sha` 和已有候选 `head_sha`；作者开始前核对仓库、HEAD、脏文件归属与当前写入窗口。绝对工作区位置不进入持久产物，正式证据使用[生命周期](artifact-lifecycle.md#持久文件路径)规定的身份和路径。
- 尚未集成的普通修正在原候选上继续追加提交；需要换到新的集成或失败修复基线时，先确认上一作者已停止、工作区干净且旧候选已保全，再由 Planner 显式切换 detached 基线。不能 reset、自动 stash、丢弃或夹带上一作者改动。中断恢复优先定位原 worktree 与精确 HEAD，禁止仅因会话丢失重建候选。
- **保全先于换基线或回收。** 所有已发布候选及其代码/报告引用对象，包括被拒绝、BLOCKED 或已取代的旧版，都须可恢复。逐项核对它们仍由持久 Git 历史可达，或已保存到核验过的持久 bundle；reflog、悬空对象、当前 worktree、`.local` 和仅存 SHA 的文本不构成持久保全。
- squash 等不保留候选血缘的策略，或换基线会失去旧候选来源时，在原候选仍是该 worktree 的 HEAD 时用原生 `git bundle create <durable_path> HEAD` 保存完整历史；覆盖不了的旧候选须分别从其精确来源保全，不能只备份最终 HEAD。运行 `git bundle verify` 后还必须在隔离恢复仓库实际恢复，逐项核对完整 SHA、所需对象字节和差异可读性。不得用新增临时分支或标签代替此保全步骤。
- bundle 放在符合证据保留要求的持久产物位置，现有报告/证据字段记录候选 SHA、产物身份与恢复命令/结果；不能放在待删除 worktree 中成为唯一副本，也不依赖 `.local`。遵循既有文件跟踪、体积、脱敏与授权限制；无法持久保全时停止换基线或回收并保留原工作区，不能宣称已可恢复。
- 回收前再次确认没有活动写入者、未提交/未跟踪的用户文件或唯一证据，并核对全部发布候选的恢复来源。只清理本次已确认可回收的精确 worktree，不强制删除，不批量清理历史分支、标签或未知工作区。

## 脏 worktree 保护

绝不能 reset、clean、丢弃、覆盖、自动 stash 或悄悄提交既有改动。记录脏文件及其与 Task 的重叠情况。若不存在重叠，并且条件允许，应从已知已提交 SHA 按上述显式命令创建干净 detached worktree；保留原工作区和用户改动。若重叠工作无法在不造成丢失或错误归属的情况下隔离，则标记 `BLOCKED` 并说明需要用户作出的决定。

## 并发

只有在以下条件全部满足时独立 Task 才能并行工作：不存在 DAG 依赖；不共享公开契约、数据库或构建配置；写路径不重叠；各自使用独立 detached worktree，每个区域只有一个写入者。只读侦察可以并行。同一 Task 内作者交接和共享遗留区域默认串行；有 worktree 不代表已解除契约或运行环境冲突。

## 跟踪分类与授权

业务仓库默认提交 `.devflow/changes/<REQ-ID>/` 下的 `state.yaml`、`current.md`、`test-plan.md`、`evidence.md`，以及必要脱敏验收附件、正式快照与迁移索引；可引用满足身份和保留期限的现有仓库/CI 产物。不跟踪临时 Prompt、搜索输出、Diff 中间件、调试日志、临时报告、会话 ID/cursor/PID/机器缓存，它们放在 `.local/`。失败/BLOCKED/not_run 的正式结果仍须持久化，不能统统归为临时文件。

Planner 在业务 Git 仓库中主动检查实际忽略规则，已有有效等价规则时复用，不重复追加。规则缺失且当前任务允许修改仓库时，主动向仓库根 `.gitignore` 追加以下规则；文件不存在则创建，保留已有内容和未提交修改，不等待用户再次提醒：

```gitignore
/.devflow/changes/*/.local/
```

用 `git check-ignore -v --no-index <path>` 核验当前 Root 的 `.local/` 内路径被忽略，四个核心文件与必要附件未被误忽略；用 `git ls-files` 检查已跟踪文件，ignore 不会自动取消跟踪。已跟踪临时文件只在明确授权和确认不丢唯一证据后用精确路径处理，敏感历史另行求解，不能用 ignore 掩盖泄漏。

无 Git、只读、明确禁止修改或存在规则冲突时，保留原内容并说明具体缺口，仅停止该配置动作；不自动删除或放宽已有忽略规则。

**Skill 源码仓库**的 `.devflow/changes/` 排除规则仅用于防止提交演示产物，不能照搬到业务仓库。凭据和未经脱敏数据不得进入受跟踪产物或外部上传。

文件应当跟踪不等于获准 commit/push；宿主规则与用户授权分别控制提交、创建标签和远端发布。无 Git、证据不允许跟踪或无提交授权时，正式送审使用[生命周期](artifact-lifecycle.md)规定的不可变本地快照，明确仅本地可恢复；要求真实代码 SHA 的门禁仍不可伪造通过。

## 提交边界与两种身份

- 草稿连续修改，不为每次编辑/commentary 提交。
- 正式送审前固定有关文档版本；代码审核前固定完整候选提交（包含测试、生成物和必要文档）。
- 同一 Task 的生产与独立测试代码由各自作者在 Planner 安排的串行写入窗口完成；作者分别固定报告的真实 SHA 范围，Planner 汇集报告并交付完整候选 G5。G5 后的测试修正也须重新审核、集成和验证，不能混入先前受测 SHA。具体顺序见[测试代码交付](../shared/test-code-delivery.md)。
- 验收或状态切换时合并提交对应证据与状态，精确路径暂存，检查 staged Diff 和既有改动归属。
- 文档身份为完整 Commit SHA + 路径 + 对象 ID；代码证据仍为 `base_sha/head_sha/tested_sha`。
- 后续追加证据的提交不等于已受测代码候选，不需要文档记录保存自身提交 SHA。引用早先已存在的文档 Commit，避免自引用造成无限补提交。
- 新提交若只追加过程证据且代码树未变，也不能改写旧测试 SHA；由独立角色说明适用范围，宿主要求新 SHA 测试时照做。

迁移需额外保留持久基线标签、全文件索引及独立审核，详见[无损迁移](../shared/legacy-migration.md)。正常维护不得移动/删除基线标签；推送迁移结果必须在授权内同时发布基线引用并验证远端恢复，不能仅发布精简分支。
