# 门禁策略

先选择本次交付路径，再判断门禁是否适用。以下 G0–G10 用于完整研发；[轻量维护](#轻量维护)按其有限完成清单执行，不因位于开发仓库、修改多个指令文件或已有历史 Root 而自动进入完整链。两条路径都必须保留真实证据、现有授权、兼容与不可变历史，不得伪造未执行的 Gate。

## 轻量维护

适用于目标清楚、范围可定位、可回滚的指令包、文档、示例、测试说明及受管配置一致性维护。指令文字含有行为调整不自动升级；重点核对实际影响。涉及业务运行代码、公共 API/数据格式、生产数据/基础设施、角色权限或安全边界、模型/配额默认值、不可兼容的报告 Schema，或无法界定消费者影响时，进入完整流程。用户明确选择路径优先；其授权不能替代真实验证或权限边界。

在现有会话或现有 notes 中一次写清目标、保持项、允许范围、必需验证和交付/停止条件。主会话直接执行维护，未进入 Planner 身份；不为此创建 Root、Task DAG、独立 Spec/计划批准链或 G0–G10 状态。已有完整 Root 不自动迁移、关闭或改判；用户另行明确选择维护时，仅记录本次范围及与旧记录的关系。不新增业务角色、Skill、必填字段或状态。

流程为修改、受影响检查、必要复核、授权交付和结束。主会话可直接编辑该维护范围；需要独立复核时默认只对最终候选做一次综合复核，返修只查实际 Finding 与 Delta。不创建审阅者来批准“无需额外审阅”，不默认派齐四角色；未派发角色不要求其原生配置/加载齐备。真实调用仅在相关行为改变或现有证据有具体缺口时执行，纯版本记账不重复研究。

开始交付前固定所需证据集合；用内容与必要输入身份核对已审/已测树到最终提交的对应，按[证据复用](change-control.md#按实际差异复用证据)补受影响部分。旧报告不改 SHA、不伪装新运行。没有完整流程的门禁身份就不宣布 G5/G6 等通过；维护完成可直接说明目标和验证结果，无需等待一个未创建的 Root 达到 DONE。

目标及保持项通过、实际风险已处理、授权交付和必要读回完成后结束。提交/推送/安装各自遵从用户授权，单次目标读回足以覆盖的阶段不再追加同类证明。额外建议、无因果依据的环境漂移和更高权威的未验证切片分别记录，不自动扩大本次目标；具体判断见[环境漂移分级](../shared/repository-discovery.md#环境漂移分级)和[收尾与有效进展](../shared/orchestration.md#收尾与有效进展)。若发现真正越过维护边界的风险，保全已有成果并只升级受影响部分，不从零重做全部阶段。

## 完整研发门禁

门禁用于防止某个角色把自己的断言直接变成交付事实。

| 门禁 | 必需输入 | 通过证据 | 决策所有者 |
|---|---|---|---|
| G0 需求接收 | 开发请求 | Intake（v2 为 current 中的对应章节；v1 为 intake.md） | 规划者 |
| G1 仓库基线 | Brownfield 范围 | 仓库画像、接管评估、基线；风险要求时还需审核 | 审核者 |
| G2 Spec | Root Issue、Spec、UI/技术决策、DAG | 对应版本的 `SPEC_REVIEW: APPROVE` | 审核者 |
| G3 用户批准 | 已审核的产品行为与重要取舍 | 绑定 Spec 版本的用户批准 | 用户 |
| G4 测试计划 | 已批准 Spec | 对应计划版本的 `TEST_REVIEW: APPROVE` | 审核者 |
| G5 Task 代码 | 已批准 Task 的完整候选及各代码作者报告，含必要测试 | 对应 SHA 范围的 `CODE_REVIEW: APPROVE` | 审核者 |
| G6 Task 集成 | Task 已合并至集成分支 | 对应 SHA 的增量测试 `PASS` | 测试者 |
| G7 完整验证 | 所有 Task 均已验证；末 Task 可按下节条件批量执行 | 对应集成 SHA 的独立完整测试报告 `PASS` | 测试者 |
| G8 发布 | 当前验证证据及迁移/配置/回滚文档 | 对应 SHA 的 `RELEASE_REVIEW: APPROVE` | 审核者 |
| G9 合并后验证 | 已合并至实际目标分支 | 对应目标 SHA 的冒烟测试 `PASS` | 测试者 |
| G10 完成 | 所有证据均为当前有效 | 关闭记录及 `DONE` 状态 | 规划者 |

事实预检、交付规模判断和目标仓库协议映射是进入首次 G2 前的准备工作，不新增 Gate 或状态。目标仓库已有证据只有在语义范围、独立决策所有者、版本/SHA 绑定和时效性均等价时，才能直接满足对应 Gate；`state.yaml` 引用其原始身份，不复制内容。规则冲突时执行更严格的一项。

环境或授权缺失应尽量限定到可独立验证的 Task/切片。低权威的合成、本地或 Mock 结果不能替代 G6–G9 要求的集成、live 或目标分支证据；不可拆分的必需证据缺失时，对应 Gate 必须保持未通过。

## 最后 Task 的 G6 与 G7 条件批量执行

最后一个 Task 已集成、其余 Task 的验证证据有效且没有后续待集成候选时，Planner 应检查是否可用一次 Tester 派发执行“先 G6，通过后 G7”。交接固定同一完整集成 SHA、Spec/测试计划修订、实际测试代码及外部资产身份、环境/配置/依赖、数据条件和两阶段命令覆盖；任一身份未知或不一致时不合并执行。此条件是既有门禁的一次批量交接，不新增 Gate、状态或报告格式。

Tester 先完成增量验证并生成独立 G6 原模板报告；只有 G6 为 PASS 且上述身份未变，才继续完整验证。G7 可引用本次或此前由 Tester 独立执行且身份、覆盖完全匹配的有效命令结果，只运行剩余必需覆盖，明确区分引用与新运行。G6 失败或 BLOCKED 时停止 G7，保留失败及未运行原因，绝不输出 G7 PASS。发现 SHA、计划/资产、环境、数据或覆盖变化时停止旧批次复用，返回精确差异，由 Planner 决定受影响验证及下一交接。

两阶段分别保留完整报告 ID、tested_sha、范围、命令/退出码、结果与限制，不把它们折叠为一份通用 PASS。Tester 不修改状态；Planner 收到后先核对并持久化 G6 原报告，再记录末 Task 为 VERIFIED，随后才持久化/采纳 G7 原报告。G6 未有效落地或尚有其他未验证 Task 时，G7 不能成为有效门禁证据。若批次中断，按已有报告身份恢复，只补尚缺的有效覆盖。

G8 仍独立审核当前完整证据；合并实际目标分支后的 G9 仍单独派发，绑定实际目标 SHA 执行冒烟。一次 G6/G7 派发和命令复用不能替代 G9。

## 审核适用范围与直接省略

完整研发路径的 G0–G4 是当前 Root/阶段的共享准备，不为每个 Task 或实现步骤重跑；G5/G6 面向完整 Task 候选及其集成 SHA；G7–G10 面向当前交付的最终验收。角色动作不是 DAG 节点，门禁也不递归套在门禁动作上。

Tester 编写的测试属于原 Task 候选，不单独建立测试 Task。G5 后新增/修正测试代码仍使相关候选证据需要重新绑定，按[测试代码交付](../shared/test-code-delivery.md)完成代码复审与 G6；测试计划审核不能替代测试代码审核。G6 后 Task 保持 `VERIFIED`，G9 通过及关闭条件齐备后才进入 `DONE`。

Planner 在初始规划的现有 Decision/Task notes 中简记适用门禁和已有证据；不创建逐步骤审核矩阵或新 Schema。以下情况可直接不发起额外 Reviewer 调用，不必先找 Reviewer 批准“无需审核”：

- Task 内部实现顺序、检查点、自测、生成物和必要文档步骤：并入完整候选 G5，不逐项送审。
- 无相关 UI/数据/权限等边界的专项维度，以及不满足 Brownfield/Continuation 风险触发条件的额外 BASELINE_REVIEW：注明不适用依据；必须的仓库画像/基线事实仍保留。
- 对象及必要输入均未变、原绑定仍有效，或宿主已有等价独立证据：引用原身份与覆盖范围，不重复发起同模式审核。
- 仅过程清单/进度变化，或明确无语义影响的 EDITORIAL：按变更控制记录，不单独开审。

“省略额外调用/不适用”不是新的 Verdict、状态或 APPROVE。已选择完整研发且仍适用的 G2/G3/G4/G5/G8 不能因“小任务、赶时间、DAG 已冻结”跳过；不要用本条反向把符合轻量维护条件的工作拉入完整链。代码 SHA 改变、真实阻断 Finding、权限/行为/测试预期变化也不能借此沿用失效证据。Reviewer 只检查委派对象的适用维度，不要求每个步骤成为独立审核节点。宿主明确强制的审核仍执行。

## 交付深度

- `FAST`：允许紧凑的 Mini Spec 和测试计划；但仍须保留角色分离、精确证据、对行为变化的用户批准，以及所有适用门禁。
- `STANDARD`：使用完整产物和常规审核/测试深度。
- `HIGH_RISK`：增加威胁、权限、迁移、回滚、失败恢复、审计及有依据的性能覆盖。明确的风险接受只能处理 P2；P0/P1 始终阻塞。

任何角色都不能因“没有反馈”而推定通过。身份/授权/关键证据缺失导致无法审核时为 `BLOCKED`；对象可审核但有阻断 Finding 时为 `REQUEST_CHANGES`。局部修订按变更控制复核实际影响，未变对象不因父文件修订而重开门禁。
